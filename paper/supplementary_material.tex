Source:
\texttt{experiments/results/*\_identity\_latency\_failure\_*/latency\_summary.json}
and \texttt{experiments/results/failure\_latency\_aggregated.csv}.
Failure mechanics (\texttt{scripts/run-failure-test.sh}):
\texttt{jvm\_kill} sends SIGKILL to the worker container and restarts
the same container 5 seconds later (local state volume intact);
\texttt{broker\_kill} stops and restarts the Kafka container 5 seconds
later; \texttt{node\_loss} removes the worker container and its
anonymous volumes (\texttt{docker\ compose\ rm\ -fsv}) and recreates it
fresh 5 seconds later, forcing full local-state loss. All six runs
matched 2000/2000 expected output records with zero missing, zero
unexpected, zero duplicates, so no failure caused an externally visible
correctness violation, only a latency spike. Kafka Streams
\texttt{node\_loss} needed a corrected retry after a script bug made the
first attempt rejoin the wrong consumer group; the number below is from
the corrected run.

and
\texttt{experiments/results/*\_w3\_latency\_tuning\_control/latency\_summary.json}.

records/sec, so only the commit/checkpoint interval varies between the
control and tuning rows for a given engine. All four rows matched 71/71

Raising the interval 10x moves a different hop per engine: Kafka

its \texttt{suppress(untilWindowCloses())} buffer is released; Flink's

with its \texttt{EXACTLY\_ONCE} Kafka sink committing on a
one-checkpoint lag. Section 6 reads both rows together.
